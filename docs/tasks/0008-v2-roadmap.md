# 작업 0008 — v2 로드맵: 조회 로그부터 메모리 md 실전 적용까지

- 상태: **진행 중** — 단계마다 지휘부 확인 후 다음 단계
- 지시: 지휘부 · 2026-10-04 (사용자 정의 요구사항, 같은 날 순서·1조각 N기록 보강)
- 관련 ADR(제안): [0015 조회 로그](../adr/0015-query-log.md) · [0016 스키마 kind](../adr/0016-schema-kind-entity-series.md) · [0017 혼합 텍스트 수집](../adr/0017-mixed-text-ingest.md)

## 배경
- 구직 기록 외에 투자 정보까지 담아 **범용성**을 확인한다. 시계열은 투자 전용이 아니라 범용 저장 형태여야 한다.
- 스키마를 만들 때 "시계열인가, 하나씩 관리하는 기록(entity)인가"를 판단해 나눈다.
- LLM 메모리 텍스트에는 여러 테이블로 나뉠 데이터가 섞여 있다 — 나누고, 스키마를 만들고, 근거와 함께 추출한다.
- 조회 과정(질문 → 해석 → SQL → 결과)을 검증할 수 있게 로그를 남긴다.

- pytest 전체 통과 + CI 통과
- **entity 회귀**: v3 dev 문항, M-haiku·M-opus, 100건 1회. 정확도 유지(v1.3 기준 M-haiku 25/28, M-opus 28/28). 항상 맞히던 문항이 깨지면 완료가 아니다

- 측정은 비용 추정 → 승인 → 실행

### ① 조회 로그 (ADR-0015)
- 만들 것
  - `query_log` 테이블: 시각, 호출자, 질문(원문·정규화), 경로, 상태, 해석, QuerySpec, SQL·params, 결과 수·근거 id, 경고, 단계별 ms, 토큰·비용, 오류, 스키마 버전
  - MCP `query_log`: recent, with_warnings, diverging, errors, by_path
  - 보존 상한(10,000행 또는 50MB, 우선 보존 규칙)과 `purge_query_log`
- 완료 기준
  - pytest: 모든 경로(fast·cache·llm·structured·entity·clarify·error)가 한 행씩 남음, 로그 실패가 답을 막지 않음, diverging 탐지, 상한 정리
  - 실데이터: 구직 기록 질문 몇 개를 다시 물어 로그 확인
  - 회귀: 공통 + 조회당 시간 증가 +5ms 이내
- 이후 단계는 모두 이 로그로 실사용 diverging·경고를 같이 본다.

### ② v1 잔여 (작은 것부터)
- 만들 것
  - **경과 시간 필터**(W5형): 두 시점의 차이를 필터 조건으로 쓴다(예: "지원 후 7일 넘게 응답이 없는 것"). 현재는 측정값(`avg_days_between`)으로만 있고 필터로는 없다. 두 필드 또는 필드와 @today의 차이에 `op`와 값을 둔다. 단위는 일·시간, 한쪽이 비어 있으면 제외하고 경고
  - **모호한 기준의 기본값 규칙**(D5): "최근", "오래된" 같은 기준 없는 말의 기본값을 사전에 정하고, 답에 "기본값 N일로 해석" 경고를 붙인다. 기본값은 스키마(타입별) 설정
  - **H5 해석**: 해당 문항의 실패 원인을 분석하고 규칙·사전으로 고친다. dev 문항만 보고 고치며, unseen으로 튜닝하지 않는다
- 완료 기준: SQL 단위 테스트(경계값·NULL), dev 해당 문항 통과, 회귀 공통

### ③ 투자 entity 가져오기
- 대상: 체결, 판단, 매수 기준 변경, 보유, 주시(관심 종목). 원본이 구조화된 JSON이라 ingest 없이 기존 `record`/가져오기 경로를 쓴다(구직 기록 가져오기와 같은 방식, 로컬 스크립트)
- **하위 순서**: 질문 수요가 크고 데이터가 깔끔한 쪽부터 한다. 하위 단계마다 쓸 수 있는 상태로 커밋한다.
  - ③-a 체결 기록 + 판단 기록
  - ③-b 매수 기준 변경 이력
  - ③-c 보유·주시 목록
- **스키마 확정 절차**: `propose_schema`(견본 기반) → 사용자 승인(지휘부를 거쳐 요청) → 반영. 승인 없이 스키마를 등록하지 않는다.
- 만들 것
  - 투자 스키마(공개 저장소에는 가상 예시 스키마와 가상 픽스처만)
  - 종목 엔티티와 참조(ref). 체결·판단은 종목을 참조하고 값을 복사하지 않는다
  - **스키마 간 관계 설명**(ADR-0017 "이중 집계 방지"): 사전에 관계 한 줄을 두고 해석기에 보여 준다
  - 멱등 가져오기 명령(아래 "기존 파일과의 관계")
- 완료 기준
  - pytest: 가상 투자 픽스처로 질의(종목별 체결 수, 기준 변경 이력, 주시 목록), 체결·판단 이중 집계 없음, 가져오기 두 번 실행 시 변화 없음, 바뀐 값은 정정 이벤트, 사라진 기록은 보고만
  - 실데이터: 사용자 투자 JSON 가져오기 → 건수 대조(원본 건수 = 저장 건수)
  - **실데이터 질문 대조표**: 지휘부가 정한 실데이터 질문 6개(체결 일시·가격, 올해 손절 종목, 매수 보류 사유, 종목 제거 시점과 사유, 매수 밴드 마지막 변경일, 주시 종목과 상태)를 Mnemento로 답하고, 원본 파일에서 직접 찾은 답과 나란히 놓은 표를 보고한다. 질문 원문과 표는 실데이터라 로컬 메모와 지휘부 보고에만 둔다.
    - 해당 없으면 "없다", 원본에 근거가 없으면 "기록 없음"이 정답이다. 지어낸 답은 실패다.
    - 근거가 서술형 문서(md)에만 있고 ③의 JSON 경로로 들어오지 않은 질문도 "기록 없음"이 정답이다. 이 질문은 Mnemento가 갖지 않은 근거를 지어내지 않는지 보는 문항이 된다. 같은 질문을 ⑥ 완료 기준에서 다시 묻는다.
  - 회귀 공통(구직 entity 질의가 투자 스키마 추가로 흔들리지 않는지 확인)

- **결과(2026-10-05, 지휘부 검수: ③a·③b 통과, ③c 적용)**
  - 스키마: security(코드 식별자), trade, decision, buy_criteria(v2), holding. 모두 사용자 승인으로 실DB에 등록했다. 공개 저장소에는 가상 예시만 있다(examples/investment).
  - 일반 기능: 멱등 가져오기(mnemento.importer: 정정·갱신·사라짐 보고·소유 필터), 관계 설명과 그에 따른 스키마 선택, 외부 식별자 우선 이름 해석(ADR-0019), 해석기 지문을 넣은 계획 캐시 키
  - 실데이터 질문 6개: 지어낸 답은 0건이다. Q5는 부분 정답(밴드 재설계일만 답하고 환율 재계산일은 빠짐)이고, Q6은 워치 설정 기준으로 답한다(포트폴리오 메모에만 있는 주시 2건은 빠짐).
  - 평가액(앱 실측 스냅샷, 모의 일일 이력)은 ⑤ series로 미뤘다.

### 기존 파일과의 관계 (③·⑤ 공통)
- 매일 루틴(오늘 확인·마감)은 당분간 지금처럼 원본 프로젝트의 JSON 파일에 쓴다. Mnemento는 그 내용을 정기적으로 옮겨 오는 **사본**이다.
- 그래서 가져오기는 여러 번 돌려도 안전해야 한다(**멱등**).
  - 이미 있는 사실은 다시 넣지 않는다(원본의 식별자 또는 identity 규칙으로 같은 기록을 찾는다).
  - 바뀐 값은 **정정 이벤트**로 넣는다. 근거는 원본 파일과 수집 시각이다.
  - 원본에서 사라진 기록은 자동으로 삭제하거나 철회하지 않고 **보고만** 한다.
  - 가격 series(⑤)는 새 날짜만 추가한다. 같은 날짜의 값이 바뀌면 batch 기록을 남긴다(ADR-0016).
- 실행 방식: 사용자가 부르거나 루틴 끝에 한 줄로 붙일 수 있는 **로컬 명령**(저장소 밖 로컬 스크립트)으로 둔다. 실행 결과는 추가·정정·변화 없음·사라짐 건수를 요약한다.
  - 원본 프로젝트의 루틴 파일은 수정하지 않는다. 루틴에 붙이는 일은 지휘부가 사용자 승인을 받아 따로 한다.
- **보류 결정**: 정본을 Mnemento로 옮길지는 써 본 뒤에 사용자가 정한다. 그때까지 정본은 원본 JSON이다.

### ④ 스키마 kind와 series (ADR-0016)
- 만들 것: `kind`, series 정의, `series_points`·`ingest_batches`, 같은 시점 갱신 + batch 되돌리기, propose_schema의 kind 판정, series QuerySpec(범위·집계·버킷·이동창·기준선·경고)
- 범용성 픽스처: 가상 **체중**, 가상 **일별 지출**(투자 가격은 ⑤)
- 완료 기준
  - pytest: 판정 신호·반례 4개, 갱신과 되돌리기, 질의 기능별 SQL 테스트, 두 도메인에서 같은 질의 동작
  - series 평가셋: 가상 문항(dev와 unseen 분리, unseen은 지휘부 작성), 정답은 생성기 원본으로 계산
  - 실데이터: 없음(⑤에서 처음)
  - 회귀 공통

### ⑤ 투자 가격 series + 연결 질의
- 만들 것: 가격 series 가져오기, `ref_series` asof 조회, "평가 손익 = 보유 수량 × 마지막 가격 − 매수 금액" 같은 질의
- 완료 기준
  - pytest: asof 규칙(직전 점, 공백 경고), 평가 손익 계산(가상 픽스처, 손계산 정답과 일치)
  - series 평가셋에 투자 가격 문항 추가(dev/unseen)
  - 실데이터: 가격 가져오기 → 몇 종목의 평가 손익을 원본 계산과 대조
  - 회귀 공통 + ④ series 문항

### ⑥ 혼합 텍스트 ingest (ADR-0017)
- 만들 것: 분할 → 분류 → 새 타입 스키마 제안(kind 포함) → 근거 검사 추출 → 1조각 N기록·N조각 1기록 처리 → 동일 엔티티(자동 병합 금지) → 미리보기 → 승인 후 한 batch 반영·되돌리기. 형제 기록 정정·철회 알림. not_data는 원문 참조만. MCP `ingest_preview`, `ingest_apply`, `ingest_revert`
- 평가: 공개 가상 라벨셋(메모리 md 흉내). **1조각→N기록, N조각→1기록, 충돌** 케이스를 포함하고 정답 라벨을 둔다
- 지표: 분류 정확도, 추출 정밀도·재현율(필드 단위), 원문에 없는 값 0건, kind 판정 정확도, 오병합 0건, 형제 묶음 정확도, 충돌 탐지 재현율
- 완료 기준
  - pytest: 근거 검사, 미리보기 = 반영 결과, batch 되돌리기, 형제 정정 경고(자동 전파 없음), N조각 1기록 병합과 충돌 보고
  - 가상 라벨셋 지표 보고
  - 실데이터: 사용자 투자 기록 텍스트(③에서 JSON으로 들어간 것과 대조 가능한 부분) → 지표를 로컬에서 보고
  - 회귀 공통 + series 문항
  - **③ 대조표에서 md에만 근거가 있던 질문**(예: 종목 제거 시점과 사유)을 다시 묻는다. ③에서는 "기록 없음"이 정답이었지만, ⑥ 이후에는 원문 근거와 함께 실제 이유가 나와야 정답이다.

### ⑦ 메모리 md 실전 적용
- 대상: Claude 메모리 md(경로는 지휘부가 따로 전달)
- 완료 기준
  - 미리보기 보고 → 사용자 승인 → 반영 → 몇 가지 질문으로 확인. 숫자 요약(조각 수, 분류 분포, 기록 수, 애매·충돌 수)만 보고
  - 되돌리기 시연(batch 하나 되돌리고 다시 반영)
  - 회귀 공통
  - README에 "텍스트 기억을 장부로" 사용법 절 추가(가상 예시)

## 백로그
- 모호한 말의 기본값은 그 표현이 나온 부분에만 적용한다(규칙 후보). ② 회귀에서 haiku가 D5의 "빠르게" 기본값을 질문 전체에 적용해, 빠르게 열람된 건만 놓고 평균을 냈다.
- measure의 `where`에서도 `elapsed`를 쓸 수 있게 하기. "빠르게 열람된 곳의 결과"처럼 측정값마다 기간 조건이 붙는 질문이 대상이다(② 회귀에서 opus가 표현할 수 없다고 스스로 밝힘).
- 사용자가 정리한 실DB에 저장소 사전 개선분을 반영하는 일반 경로(제안 → 승인, ADR-0018).

## 공통 원칙(유지)
- 사실은 근거와 함께, 모르면 비워 두거나 묻는다. 스키마 확정·수집 반영은 사용자 승인으로만(approved_by + 원문 기록).
- 실데이터·실데이터 경로·로그는 공개 저장소에 넣지 않는다.
- 벤치 수치는 측정한 버전 기준으로만 싣고, 새 버전은 회귀 측정과 새 미노출 문항으로만 주장한다.
