# 작업 0007 — v1.3: 스키마 밖 기록을 버리지 않기 (보류 쓰기 + 한 번에 승인) — 초안

- 상태: **초안** — 지휘부 검수 후 구현
- 근거: 사용자 질문 "플랫폼이나 속성이 추가돼도 저장·조회가 원활한가?"에 대해 실제 DB 사본으로 확인한 현재 동작(2026-10-04)

## 현재 동작 (사실 확인 결과)
| 경우 | 지금 | 문제 |
|---|---|---|
| enum 밖 값 (`platform="remember"`) | 검증 실패로 거부, 저장 0 | **관측조차 안 됨** → 확장 제안이 생기지 않음 |
| 스키마 밖 필드 (`applicants=25`) | 거부, 저장 0, 관측만 남음(샘플 5개) | 값 자체는 사라짐(실데이터 25건의 지원자 수 유실) |
| 확장 적용 | Python API(`schemas.register`)로만 가능, MCP 도구 없음 | 사용자가 대화 중에 승인할 수 없음 |
| 적용 뒤 | 다시 보내야 저장됨, 예전 시도는 자동 반영 안 됨 | 승인 전까지 기록이 아예 없음 |
| 예전 기록에 새 필드 조회 | 값이 있는 기록만 셈, **경고 없음** | "39건 중 1건 기준"이라는 걸 모름 |

## 만들 것
1. **보류 쓰기(pending)** — 스키마 밖 필드나 enum 밖 값 때문에 검증에 실패한 쓰기는 버리지 않고 `pending_writes`에 원문 그대로 보관한다(요청, 이유, 누가, 언제). 응답 상태는 `pending`이고, 무엇이 승인되면 반영되는지를 알려 준다.
   - 기록 자체는 저장되지 않는다(정본 오염 금지). 보류는 현재 상태·질의에 보이지 않지만, 목록과 개수를 조회할 수 있다.
   - enum 밖 값도 관측해서 확장 제안을 만든다(`extend_enum`).
2. **확장 승인 = 스키마 확장 + 보류 반영을 한 번에** — MCP 도구 `apply_schema_proposal(proposal_id, labels?, descriptions?)`
   - 스키마를 추가형으로 한 단계 올린다(ADR-0005 검사 통과 필수). enum 값을 추가할 때는 **라벨(한국어 이름)도 함께** 받는다(예: remember → 리멤버).
   - 그 확장으로 통과하게 되는 보류 기록을 **재검증해서 자동 반영**하고(정상 쓰기 경로, 근거에 "보류 → 승인 반영" 기록), 여전히 실패하는 것은 보류에 남긴다.
   - 결과: 확장된 버전, 반영 N건, 남은 보류 M건(이유별).
   - 대화 흐름: record가 `pending`과 함께 "remember 플랫폼을 추가할까요?"라는 질문과 제안 id를 돌려주고, 사용자가 예라고 하면 에이전트가 이 도구를 한 번 부른다.
3. **거절** — `reject_schema_proposal(proposal_id, keep="drop_fields" | "discard")`. 보류 기록을 정리하거나, 문제 필드를 뺀 채 저장할지 선택한다(뺀 채 저장할 때는 근거에 무엇을 뺐는지 남김).
4. **조회 경고** — 필터·그룹·측정에 쓰인 필드가 없는 기록이 있으면 "N건은 이 필드가 없음(추가 전 기록 등)" 경고를 낸다(ADR-0013의 applied_at 경고를 날짜 필드 밖으로 일반화).
5. **dogfooding 재가져오기** — 지원자 수·열람 소요 시간을 보류로 보관하고, 사용자가 확장을 승인하면 반영되는지 실데이터로 확인한다.

## 원칙
- 스키마는 조용히 바뀌지 않는다: 확장은 사용자(또는 지휘부) 승인으로만, 추가형 변경만.
- 보류는 정본이 아니다: 질의 결과에 섞이지 않고, 반영될 때 정상 쓰기 경로(검증·이벤트)를 탄다.
- ADR 하나로 결정을 기록한다(보류 저장 위치, 제안 id, 재검증 규칙).

## 완료 기준
- pytest: enum 밖 값 보류 + 제안 생성 / 필드 밖 값 보류 / 승인 → 스키마 v+1 + 보류 자동 반영(재검증 포함) / 일부만 통과하는 경우 / 거절 두 방식 / 라벨 필수 / 조회 경고 / MCP 도구 왕복
- 실데이터 사본으로 a~d 시나리오 재현 결과 보고
- 벤치 재측정 없음
