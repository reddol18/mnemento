# 작업 0004 — v1: 정확도 보강 + 평가 하네스 v2 (초안)

- 상태: **승인** (지휘부 검수 2026-10-03, 조건 4건 반영)
- 작성: 구현 에이전트 · 2026-10-03
- 근거: v0-reduced 측정 결과(`bench/results/v0-reduced-haiku/` report·NOTES), PLAN 2-1, ADR-0008·0010·0011

## 배경
v0-reduced(haiku, 12문항 × 3회)에서 Mnemento(M)는 속도·토큰에서 모든 규모에 크게 앞섰다(문항당 약 15초, 입력 약 4k 토큰, 규모와 무관). 반면 정확도는 100건에서 B1(Claude Code 메모리)에 졌다(23/36 대 28/36). M의 오답은 대부분 아래 세 가지 원인이다.
1. **이력 대 현재 상태 혼동(H2)** — "열람된 지원"을 현재 status로 해석
2. **QuerySpec 표현력 공백(H3·H4)** — 그룹 크기 조건, 이벤트 시각 정렬. 여기에 변환기의 개수 처리 문제(H4)가 겹침
3. **하네스 문제** — 형식 힌트가 B0·B1에만 주어짐(D4), 생성기 별칭 중복(U2 10k)

v1은 ①②로 M을 고치고, ③으로 공정한 하네스 v2에서 다시 잰다. **v0 결과는 덮어쓰지 않는다.**

## 만들 것 (우선순위 순)

### ① 이력 기준 해석 규칙 (H2)
- "~된 적 있음 / ~까지 간 / 열람된 지원"처럼 **도달 여부**를 묻는 표현은 현재 status가 아니라 **이벤트 이력**으로 판단한다.
- 구현 방향: **(b) `reached` 필터로 확정**(ADR-0012). 정본은 이벤트 이력이고(ADR-0003·0007), 날짜 필드는 비어 있거나 정정될 수 있다.
  - QuerySpec 필터 `op: reached`(status 필드 전용): 그 상태에 **한 번이라도 도달**했는지. 정정·철회를 반영한 재생 결과로 판단한다.
  - 스키마 사전: status 필드에 "도달 가능한 단계"와 함의 관계(`implies`, 예: passed는 viewed를 거친 것)를 설명으로 추가해, LLM이 reached를 고를 수 있게 한다.
- 검증 규칙: 해석 결과가 "상태 in (중간 단계 일부)"로 도달 여부를 근사하면 경고하거나 거부한다.
- 테스트: 열람 후 불합격·합격한 건이 "열람된 지원"에 포함되는지 확인.

### ② QuerySpec 확장 + 변환기
- `having`: 그룹 결과에 대한 조건(예: `count >= 2`). 측정값 이름이나 `count`만 쓸 수 있고, 값 바인딩.
- 이벤트 시각 정렬: `order_by_event: {kind, to}`. 해당 이벤트(무효 제외)의 시각으로 정렬하고, list 모드 `limit`과 함께 쓴다(예: 최근 불합격 3건).
- 답변 변환기: list 모드에서 `limit`으로 잘린 경우 `number`는 **보여 준 건수**로 하고, 전체 개수는 따로 표시(H4).
- 기존 검증 원칙 유지: 스키마 밖 필드·허용값 밖 값 거부, SQL은 코드가 생성.

### ③ 평가 하네스 v2 + 평가셋 v2
- **형식 힌트 공정화**: v1은 (i) **모든 비교군에 같은 형식 힌트**를 주는 조건 하나로 측정한다(M의 해석 단계에도 같은 힌트를 전달). (ii) "힌트 없음 + 자유 서술 채점"은 채점 방식 신설과 측정 비용 2배가 필요하므로 **후속 과제**로 둔다.
- **생성기 v2**: 별칭이 회사 간에 겹치지 않게 하고(전역 유일), 같은 회사가 다른 이름으로 중복 기록된 경우를 일부 생성해 별칭 묶기를 실제로 검증한다. 평가셋 이름은 `v2`로 하고, v0 결과와 디렉터리·표기를 분리한다.
- **미노출 문항 추가**: 새 unseen 문항을 지휘부가 독립적으로 작성한다(구현자는 정답 계산 코드만). v0 문항 20개는 dev로 옮긴다(v1 개발 중 사용했으므로).
- 하네스 기능: run 메타에 평가셋 버전·힌트 조건 기록, report에 v0/v2를 섞지 않는 필터.
- **비용 상한을 하네스에 내장**: `--max-cost`(정가 누적이 넘으면 정상 종료). 외부 감시 도구를 쓸 때는 프로세스를 셀 때 자기 자신과 자식 프로세스를 뺀다(v0 측정 때 감시 프로세스가 자기를 세어 끝나지 않던 문제).
- **미노출 문항**: ①②가 구현된 뒤, 측정 전에 지휘부가 `docs/eval/`에 따로 작성해 전달한다. 그때까지 unseen은 비워 둔다.

### ④ 회귀 확인 (측정 전, 승인 불필요)
- ①② 구현 후 v0 평가셋의 dev 문항으로 **M만** 100건·1,000건에서 각 1회 실행해, 이미 맞히던 문항(D1~D3, U1, U3, H1)이 깨지지 않았는지 확인한다. 결과는 run `v1-regression`으로 남기고 v0 결과와 섞지 않는다.

## 과적합 방지 (유지)
- **시드 분리**: v2 측정용 시드는 개발용 시드와 다르게 하고, 측정 전까지 그 시드의 데이터로 질의를 돌려 보지 않는다.
- **프롬프트·규칙 고정**: 측정 시작 전에 커밋하고, 고정 해시를 run에 기록한다. 측정 중에는 고치지 않는다.
- **미노출 문항**: 지휘부가 작성하고, 구현자는 측정 전에 미노출 문항으로 M을 돌려 보지 않는다(정답 계산 검증은 손으로 쓴 참조 QuerySpec으로만).
- ①②는 v0 문항(dev)과 새 개발용 문항으로만 개발한다.
