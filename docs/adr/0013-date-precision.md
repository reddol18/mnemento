# ADR-0013: 날짜·시각 정밀도 — 모르는 날짜는 비워 두고, 이벤트 시각에는 정밀도를 기록한다

- 상태: 채택 · 2026-10-04 (작업 0006, dogfooding에서 발견)

## 맥락
실제 구직 기록을 가져와 보니(dogfooding) 지원일이 적혀 있지 않은 기록(9월 사람인 12건, 이전 원티드 6건)과, 날짜만 알고 시각은 모르는 사건(열람일 "9/18")이 많았다. v1.1까지는 `applied_at`이 필수였고, 이벤트의 `at`은 오프셋을 포함한 정확한 시각만 받았다(ADR-0004). 그래서 가져오기 도구는 날짜를 지어내거나(금지) 가져온 시각을 사건 시각처럼 기록하는 수밖에 없었다. 그렇게 하면 "열람까지 몇 시간"·"최근 열람 순서" 같은 이벤트 시각 기반 질의가 조용히 틀린다.

## 결정
1. **모르는 날짜는 비워 둔다.** `application.applied_at`은 필수에서 **선택**으로 바꾼다(application 스키마 v3, 추가형 변경 — ADR-0005). 날짜 필드로 거르거나 묶는 답에는 "그 날짜가 없는 기록 N건은 세지 않았다"는 경고를 자동으로 붙인다.
2. **이벤트 시각에 정밀도를 기록한다.** 이벤트에 `at_precision ∈ {time, date, unknown}`(기본값 `time`)을 둔다.
   - `time`: `at`이 실제 사건 시각
   - `date`: 날짜만 앎. `at` = 그날 00:00(사용자 시간대)
   - `unknown`: 사건 시각을 모름. `at` = 기록한 시각(순서 유지용일 뿐 사건 시각이 아님)
3. **시각 기반 계산은 `time` 정밀도만 쓴다.** `avg_hours_between_events`와 `order_by_event`는 두 사건 모두 `time`인 기록만 사용하고, 빠진 기록 수를 답의 경고로 알린다. 날짜 필드(`viewed_at` 등)는 정밀도와 관계없이 날짜 단위로 쓴다.
4. **재생 순서**: 시각을 모르는 이벤트(`unknown`)는 자리표시 시각이 아니라, **그보다 먼저 기록된 이벤트 중 시각을 아는 것의 가장 늦은 시각 바로 뒤**에 놓는다(기록 순서 유지). 자리표시 시각(기록 시각)으로 정렬하면 "오늘 기록한 날짜 미상의 열람"이 "9/18 탈락"보다 뒤로 가서 상태 전이가 충돌한다(dogfooding에서 실제로 발생, 회귀 테스트 있음).
5. 기존 데이터베이스에는 열을 추가한다(기본값 `time` — 그 전의 이벤트 시각은 모두 정확했다).

## 대안
| 대안 | 기각 이유 |
|---|---|
| 지원일 대신 가져온 날짜를 넣기 | 사실이 아님. "9월 지원 몇 곳"이 틀린다 |
| 필드마다 `_precision` 짝 필드 | 스키마가 두 배로 늘어나고 LLM 사전이 복잡해진다. 날짜 필드는 "없음"으로 충분하다 |
| 시각 정밀도 없이 `at`만 두기 | 시각 기반 질의가 섞인 정밀도를 구분하지 못한다 |

## 결과
- 측정된 벤치마크 버전(고정 해시 2c56c658bc5f10f9)에는 이 변경이 없다. 벤치 데이터는 모두 정확한 시각이라 결과에 영향은 없지만, 재측정 전에는 같은 버전이라고 주장하지 않는다.
