# ADR-0010: 질문 파이프라인 — QuerySpec 중간 표현, 코드가 SQL 생성, 정형 질문은 LLM 없이

- 상태: 채택 · 2026-10-03

## 맥락
PLAN 2-1은 정확도는 LLM 메모리 이상, 속도·비용은 더 낫게를 요구하고, 5-1 A는 해석 → 질의 정의 → 답변 3단계를 정했다. 작업 0002는 "LLM에는 관련 스키마 일부와 집계 결과만", "SQL은 코드로", "정형 질문은 LLM 없이"를 원칙으로 줬다. 구현하면서 정한 세부 사항을 기록한다.

## 결정
1. **QuerySpec이 유일한 중간 표현** — `entity_type`, `mode`(count|list|aggregate), `filters`(eq·ne·in·not_in·gt·gte·lt·lte·exists·missing·contains·name_is), `group_by`(날짜는 day/week/month/year 버킷), `measures`(count·count_if·sum·avg·min·max·avg_days_between, 모두 `where`로 좁힐 수 있음), `list_fields`, `order_by`, `limit`, `interpretation`. Pydantic 모델이고 JSON Schema가 그대로 LLM 구조화 출력 스키마가 된다. 다른 에이전트도 같은 QuerySpec을 MCP로 직접 보낼 수 있다(LLM 0회).
2. **검증 = 환각 차단** — 필드는 스키마 사전에 있어야 하고, enum 필드 값은 허용값 안에 있어야 하며, 날짜 필드는 `YYYY-MM-DD` 또는 상대 토큰만 받는다. 실패하면 오류 목록을 붙여 **1회 재시도**하고, 그래도 실패하면 실행하지 않고 `clarify`로 돌려준다.
3. **상대 날짜는 코드가 푼다** — LLM은 `@today-1d`, `@last_month_start` 같은 토큰만 쓰고, 설정 시간대로 실제 날짜로 바꾸는 건 코드다(ADR-0004). 해석 결과는 답에 표시한다.
4. **이름으로 참조하기(`name_is`)** — 참조 필드(`ref`)는 이름으로 거를 수 있고, 코드가 ADR-0006 규칙(사업자번호 → 정규화 이름 → 별칭 / 이름 필드가 없는 타입은 식별자 필드 일치)으로 id로 바꾼다. 비슷한 이름은 후보만 내고 되묻는다.
5. **프롬프트에 넣는 것** — 질문에 걸리는 스키마(키워드·라벨 일치)와 그 스키마가 참조하는 스키마만. 필드 설명·허용값·라벨, 그리고 enum이 없는 짧은 문자열 필드는 **관측된 값 목록**(서로 다른 값 12개 이하일 때만, SQL로 집계)을 넣는다. 레코드 자체는 넣지 않는다.
6. **빠른 경로(fast path)** — 질문의 모든 단어가 스키마 사전(타입 키워드, enum 라벨)·날짜·허용된 군말로 설명될 때만 규칙으로 QuerySpec을 만든다. 남는 단어가 있으면 포기하고 LLM으로 넘긴다(보수적). 엔티티 id 단독 질문도 빠른 경로다.
7. **답변** — 템플릿이 숫자·목록·그룹표와 근거 id를 쓰고, 경고를 자동으로 붙인다: 표본 수 n<5, 진행 중인 기간 버킷, 최근 3일 내 기록(결과 미확정), 결과 0건, 상대 날짜 해석, 이름 해석. LLM 서술(narrate)은 선택이며 **집계 결과만** 받는다.
8. **스키마 사전 확장(추가형 키)** — 필드 `ref`(참조 대상 타입), `labels`(enum 값 → 자연어 동의어), 스키마 `keywords`(타입을 가리키는 단어), `default_date_field`(맨 날짜가 가리키는 필드). v1 스키마 파일에 추가했다(실데이터 이관 전이라 버전 유지).
9. **LLM 어댑터** — `complete_json(system, prompt, schema)` 하나. 기본 구현은 Claude Code CLI(`claude -p --json-schema`, 도구·MCP·설정 파일 없이, 임시 작업 폴더에서). 호출마다 토큰·비용과 함께 ① CLI 오버헤드(벽시계 − API 시간) ② 모델 시간을 따로 기록한다. 테스트는 `ScriptedLLM`.
10. **SQL 방언** — 컴파일러는 SQLite 방언(생성 컬럼 `f_<필드>`, `json_extract`). 저장소 인터페이스에는 읽기 전용 `fetch_all`만 추가했다. Postgres 어댑터를 만들 때 컴파일러도 방언별로 하나 더 둔다.

## 근거
- LLM이 SQL을 쓰면 스키마 밖 컬럼·잘못된 JSON 경로·주입 위험을 매번 검사해야 한다. QuerySpec은 검증 가능한 작은 언어라 검사가 완전하고, 같은 질문 패턴의 재사용(캐시)도 쉽다.
- 답변 경고를 코드로 붙이면 LLM이 표본 수 경고를 빠뜨리는 일이 없다(평가 문항 Q4의 채점 포인트).

## 대안
| 대안 | 기각 이유 |
|---|---|
| LLM이 SQL 직접 작성 | 검증 불완전, 주입·환각 위험, 토큰 증가 |
| 전체 스키마를 항상 프롬프트에 | 타입이 늘수록 비용 증가 (PLAN 2-1 원칙 1) |
| 빠른 경로를 공격적으로(부분 일치도 허용) | 틀린 답이 LLM 비용보다 비싸다 — 정확도 우선 |

## 결과
- 실측(데모, haiku, CLI): 정형 질문 Q1은 LLM 0회 약 15ms. LLM 해석 질문은 1회 호출에 입력 약 3.8k 토큰(CLI 고정 오버헤드 약 1.2k 포함), 8~36초. 대부분 모델 응답 시간이고 CLI 오버헤드는 호출당 약 2초다. 자세한 수치는 `docs/demo/0002-demo-log.md`.
- 남은 일: 같은 질문 패턴의 QuerySpec 캐시(PLAN 2-1 원칙 4), Q5(사건 시각 기반 파생 필드)·Q6(events 대상 질의)는 QuerySpec에 `source: events`를 추가해야 한다 → 0003 전에 필요하면 확장.
- 채택 조건(지휘부 검수, 2026-10-03): LLM 서술(narrate)은 **기본 꺼짐** — 템플릿 답이 정답이고, 서술이 0/9를 "데이터 없음"으로 잘못 읽은 사례가 있었으며 비용·시간의 절반 이상을 차지했다. 벤치마크는 두 모드를 모두 잰다. 속도는 ① 해석 단계 사고 토큰 줄이기 ② QuerySpec 캐시 ③ 빠른 경로 확대를 먼저 시도하고, 그래도 지는 항목은 이유와 함께 공개한다.
