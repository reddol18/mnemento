# ADR-0014: 먼저 저장하고 나중에 정리한다 — 미등록(draft) 필드·값

- 상태: 채택 · 2026-10-04 (작업 0007, 사용자 지적: "JSON이라 유연한데, 있는 레코드만 조회하면 되지 않나?")
- 대체: ADR-0001/스키마 정의의 `additionalProperties: false`를 **쓰기 시점에** 적용하던 결정

## 맥락
v1.2까지는 스키마에 없는 필드가 하나라도 있으면 기록 전체를 거부했고(저장 0), enum 밖 값(`platform="remember"`)은 관측조차 되지 않았다. 실제로 써 보니 새 플랫폼으로 지원한 기록이 승인 전까지 아예 남지 않았고, 가져온 실데이터의 지원자 수 25건이 사라졌다. 문서 저장소(JSON)의 유연성을 버린 셈이었다. 반면 사전을 없애면 LLM이 필드를 짐작하는 원래 문제로 돌아간다.

## 결정
1. **저장**: 쓰기 검증은 관대하게 한다. 등록된 필드의 위반(필수 누락, 타입 불일치, 날짜 형식)만 거부하고, **미등록 필드와 enum 밖 값은 그대로 저장**한다(같은 이벤트·이력 경로). 값을 바꾸거나 `other`로 변환하지 않는다.
2. **미등록(draft) 사전**: 저장된 기록에서 매번 계산한다(이름, 관측 타입, 견본, 건수, 처음 본 시각 / enum 밖 값과 건수). 별도 목록을 두지 않아 실제 데이터와 어긋나지 않는다.
3. **조회**: 해석기 사전에 draft 필드·값을 "UNREGISTERED (draft)" 표시와 함께 넣는다. 질의 검증과 컴파일은 등록 스키마 + draft를 쓴다(인덱스가 없으므로 `json_extract`로 직접 읽는다). 질문이 쓰는 필드가 없는 기록이 있으면 **항상** "N건은 이 필드가 없음" 경고를 붙인다. 한 번도 저장된 적 없는 값은 여전히 거부한다(환각 차단 유지). 식별자 형식이 아닌 draft 이름(예: 한글 필드명)은 정리 전까지 질의할 수 없다.
4. **정리(사용자 승인은 여기에만)**: `propose_schema`는 저장 허락이 아니라 정리 제안이다 — draft 필드 등록(타입·설명·인덱스), enum 값 등록(라벨 필수), 비슷한 이름 묶기. `apply_schema_proposal`은 `approved_by`와 사용자의 답을 받아야만 실행되고, `schema_changes`에 남는다. 묶기는 기존 기록을 지우지 않고 `migrated` 이벤트로 값을 옮긴다(다른 값이 이미 있으면 덮어쓰지 않고 충돌로 보고). 등록은 추가형 스키마 버전(ADR-0005).
5. **오타·파편화 방지**: 새 이름이 등록·draft 이름과 비슷하면(정규화 이름, 편집 거리, enum 라벨) 저장은 하되 "같은 뜻인가요?" 질문을 응답에 붙인다. 자동 병합은 하지 않는다(ADR-0006).

## 결과
- 승인 전에도 기록이 남고, 개수와 조회가 바로 맞는다. 대신 사전이 지저분해질 수 있어 정리 제안과 비슷한 이름 확인이 그 비용을 줄인다.
- 측정된 벤치마크 버전에는 이 변경이 없다(벤치 데이터에는 draft가 없어 해석기 사전에 draft 항목이 생기지 않는다).
- 폐기한 대안: 보류함(pending_writes) — 승인 전까지 기록이 질의에서 빠지고 흐름이 복잡해진다.
