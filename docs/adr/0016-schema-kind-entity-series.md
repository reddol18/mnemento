# ADR-0016: 스키마 kind — entity와 series(시계열)

- 상태: **승인** (작업 0008 ④⑤, 지휘부 2026-10-04)

## 맥락
지금 모든 기록은 entity다. 기록 하나마다 created·updated·status_changed 이벤트가 쌓이고, 현재 상태는 재생으로 만든다(ADR-0003). 투자 가격, 체중, 일별 지출 같은 **시계열**을 이 방식으로 넣으면 점 하나마다 엔티티와 이벤트가 생긴다(종목 10개 × 3년이면 약 7,500개). 재생할 상태 전이도 없고, 정정 단위도 "점"이 아니라 "수집 한 번"이다. 시계열은 투자 전용 기능이 아니라 범용 저장 형태여야 한다.

## 결정
1. 스키마에 `kind ∈ {entity, series}`를 둔다(기본값 `entity` — 기존 스키마는 그대로).
2. **series 스키마**
   - `series_key`: 계열을 가르는 필드 목록(예: `[symbol]`, `[person]`, `[category]`)
   - `time_field`: 시점 필드(`date` 또는 `date-time`), 그리고 `granularity`(`day`·`hour`·…·`instant`)
   - `measures`: 숫자 측정값 필드들(단위 `unit` 설명 포함). 숫자가 아닌 보조 필드(`source` 등)도 허용
   - 저장: `series_points(type, key_json, t, values_json, batch_id)` — 행 하나에 측정값 여러 개. `(type, key, t)`가 유일 키
   - 같은 시점이 다시 들어오면 **갱신**하고, 이전 값과 바뀐 값은 수집 기록(`ingest_batches`: 시각·출처·호출자·행 수·바뀐 행)에 남긴다. 점 하나마다 이벤트를 두지 않는다
   - 정정·철회는 **batch 단위**: `retract_batch(batch_id)`가 그 batch가 바꾼 점을 이전 값으로 되돌린다
3. **판정(propose_schema가 제안, 사용자가 확정)** — 견본 행에서 다음을 센다
   | 신호 | series 쪽 | entity 쪽 |
   |---|---|---|
   | 시점 필드 | 모든 행에 있고, 키당 서로 다른 시점이 여럿 | 없거나 행마다 하나뿐 |
   | 측정값 | 숫자 필드가 대부분 | 문자열·상태 필드가 대부분 |
   | 키당 행 수 | 많다(중앙값 ≥ 5) | 1 |
   | 상태 전이·참조 | 없다 | status 같은 enum이 바뀌고, 다른 기록을 참조한다 |
   | 개별 정정 | 수집 단위로 바뀐다 | 한 건씩 정정·철회된다 |
   - 신호가 엇갈리면(예: 시점 필드는 있는데 상태 필드도 있음) **판정하지 않고 묻는다**("이건 가격처럼 시간에 따라 쌓이는 값인가요, 하나씩 관리하는 기록인가요?")
   - **반례**:
     - 매매 체결 기록 — 시점·숫자가 있지만 건마다 정정·취소가 있으므로 **entity**
     - 구독료 — 매달 같은 금액이 반복되지만 "계약" 하나와 그 변경이므로 **entity**(청구 내역만 따로 쌓는다면 series)
     - 면접 일정 — 시점이 있지만 상태 전이가 있으므로 **entity**
     - 하루 한 번 재는 체중 — 상태 전이도 참조도 없으므로 **series**
4. **질의 확장(QuerySpec, SQL은 코드가 생성)**
   - `source: series`, `series: <type>`, `key` 필터, 시점 범위(상대 날짜 토큰 그대로 사용)
   - 집계: `max`·`min`·`avg`·`first`·`last`·`change`(처음 대비 마지막)·`change_pct`, 시점 버킷(일·주·월)
   - 이동창: `window: {size: 20, unit: points|days, agg: avg}` — 이동평균 등(SQLite 윈도 함수)
   - 기준선 비교: `compare: {measure, op, baseline: {window|series|value}}` — 예: "52주 평균 아래였던 날"
   - 결과 경고: 시점 공백(빠진 날 수), 표본 수, 진행 중인 기간
5. **entity–series 연결(범위를 좁혀서)**: entity 필드가 series 키를 가리키는 경우(`ref_series`)만, **"시점 t의 값"** 조회 하나를 지원한다. 예: 체결 기록(entity: 종목·수량·체결일) + 가격(series) → "현재 평가액 = 수량 × 마지막 가격". 그 외의 자유 조인은 하지 않는다(해석 오류 범위를 줄임). asof 규칙: t 이전의 가장 가까운 점, 공백이 N일을 넘으면 경고.
6. **범용성 검증**: 테스트 픽스처에 투자 가격 외에 **체중(person, kg)**과 **일별 지출(category, amount)** 가상 series를 둔다. 같은 질의 기능이 세 도메인에서 그대로 동작해야 한다.

## 대안
| 대안 | 기각 이유 |
|---|---|
| 시계열도 entity로(점 하나 = 엔티티) | 이벤트·재생 비용, 정정 단위 불일치, 사전이 점 단위 필드로 넘침 |
| 별도 시계열 DB | 설치·백업이 둘로 나뉨. 개인 규모에서는 SQLite 윈도 함수로 충분 |
| 자유 조인 허용 | LLM이 조인 조건을 짐작하면 정확도가 떨어진다(이 프로젝트의 출발점 문제) |

## 결과
- 가격·체중·지출 같은 데이터가 같은 장부에서 질의된다. 판정이 애매한 경우는 사용자에게 묻는 비용이 든다.
- entity 경로는 바뀌지 않는다 — 회귀 측정으로 확인한다.
