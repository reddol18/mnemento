# ADR-0030: 날짜 필드로 잰 간격은 맞는 이벤트 시각이 있으면 그것으로 잰다

- 상태: **승인** (사용자 승인 2026-10-12, 지휘부 권고. 이슈 https://github.com/reddol18/mnemento/issues/21)

## 맥락
미노출 v6 Z5("열람될 때까지 기다린 시간을 플랫폼별로 다 합치면 각각 며칠이야?")에서 세 모델(Haiku 4.5, Sonnet 5.5, Opus 5.5)이 모두 같은 방향으로 틀렸다. `span`의 양 끝을 날짜 필드(`applied_at` → `viewed_at`)로 골라서, 하루 단위로 잘린 일수를 합쳤다(saramin 29일, 이벤트 기준 정답 27.17일).

- 프롬프트에는 이미 "기록의 이벤트가 두 시점을 다 주면 이벤트를 써라"가 있다. 세 모델이 모두 따르지 않았으니 프롬프트를 더 고쳐도 모델이 바뀔 때마다 흔들릴 수 있다.
- 날짜 필드와 이벤트는 같은 사건을 가리킨다(`applied_at`은 생성 이벤트, `viewed_at`은 viewed로 바뀐 이벤트). 하지만 그 짝이 지금 스키마 사전에 없어서 코드는 알 수 없다.
- 이관한 기록은 생성 이벤트가 이관한 시각이다. 지원한 날이 아니다. 짝만 보고 무조건 바꾸면 이관 데이터에서 엉뚱한 값이 나온다.

## 결정
1. **스키마 사전의 날짜 필드에 `event`를 둔다.** 그 날짜가 어떤 이벤트의 날인지 적는다.
   - `applied_at`: `{"kind": "created"}`
   - `viewed_at`: `{"kind": "status_changed", "to": "viewed"}`
   - 날짜 필드(format date / date-time)에만 쓸 수 있다. `to`는 그 스키마 `status`의 허용 값이어야 한다. application 스키마는 v5가 된다(추가만 하는 변경).
2. **측정 간격(`span`)만 바꾼다.** 측정값의 `span`과 목록의 `Value.span`이 대상이다.
   - 양 끝이 모두 `event`가 적힌 날짜 필드일 때만 바꾼다. 한쪽이 오늘이거나 이벤트이면 그대로 둔다.
   - 조건(`elapsed`, 예: "지원한 지 2주 넘은")은 바꾸지 않는다. 오늘까지의 날짜 차이를 묻는 말이라 날짜 기준이 맞다.
3. **기록마다 확인하고 바꾼다.** 두 이벤트가 모두 있고 각 이벤트의 날(기록된 현지 날짜)이 날짜 필드와 같으면 이벤트 시각으로 잰다. 아니면 그 기록은 날짜로 잰다.
   - 그래서 결과가 날짜로 잰 것보다 나빠지는 일은 없다. 이관 기록처럼 이벤트가 날짜와 맞지 않는 기록은 원래대로 날짜로 계산된다.
   - ADR-0029 ⑤("이벤트로 쓴 간격에서 이벤트가 없는 기록은 빼고 알린다")와 부딪히지 않는다. 그 규칙은 해석기가 이벤트를 고른 간격의 규칙이다. 여기서는 해석기가 날짜를 골랐으므로 날짜가 기준이다. 그중 더 정확한 시각을 확인할 수 있는 기록만 정확하게 잰다.
4. **바꿨다고 답에 적는다.** "applied_at → viewed_at 간격은 날짜 대신 이벤트 시각(created → viewed)으로 쟀다"라는 경고를 남긴다. 날짜로 잰 기록이 있으면 몇 건인지도 적는다.
5. **질문이 날짜를 직접 가리키면 바꾸지 않는다.** 검증·컴파일 단계는 질문 문장을 보지 않는다. 그래서 `TimePoint`에 `as_dated: true` 칸을 둔다. 해석기는 "지원일 기준 며칠"처럼 질문이 날짜 자체를 말할 때 이 칸을 켠다. 한쪽이라도 켜져 있으면 바꾸지 않는다.
6. **명세는 그대로 둔다.** 바꾸기는 SQL을 만들 때 한다. 계획 캐시와 답의 `spec`에는 해석기가 쓴 그대로 남는다. 사전에 `event`가 없는 스키마(사용자가 정리한 스키마 포함)는 지금과 똑같이 동작한다.

## 근거
- 모델이 무엇을 고르든 같은 답이 나온다. 세 모델이 같은 실수를 했으니 해석이 아니라 계산 쪽에서 막는 편이 확실하다.
- 기록마다 확인하므로 이관 데이터에서도 안전하다. 바꿀 수 없는 기록은 원래 계산을 그대로 쓴다.
- 짝을 코드에 박지 않고 사전에 적으므로 다른 기록 종류도 같은 방식으로 쓸 수 있다.

## 대안
| 대안 | 기각 이유 |
|---|---|
| 프롬프트만 더 강하게 | 이미 있는 규칙을 세 모델이 모두 지키지 않았다. 모델이 바뀔 때마다 다시 흔들린다 |
| 검증에서 거절하고 다시 쓰게 하기 | 재시도 비용이 든다. 날짜 기준이 맞는 질문(`as_dated`)도 거절될 위험이 있다 |
| 명세 자체를 이벤트로 고쳐 쓰기 | 이벤트가 없는 기록이 빠진다(ADR-0029 ⑤). 이관 데이터에서 답의 대부분이 사라질 수 있다 |
| `elapsed` 조건도 바꾸기 | "지원한 지 2주 넘은"은 날짜 차이를 묻는다. 시각으로 재면 경계에서 답이 바뀐다 |

## 결과
- 시간 단위(`unit: hours`)와 날짜 필드의 조합은 계속 거절한다(ADR-0029 ⑤). 바꾸기는 기록마다 다르게 일어나므로 시간 정밀도를 보장할 수 없다.
- 확인은 dev에 합계·평균 문항을 하나씩 추가해서 한다(지휘부 제안). 미노출 세트는 v6에서 다 썼다.

## 후속 (같은 날)
- **사용자가 정리한 스키마에도 전달한다.** 실데이터 DB의 application은 사용자가 정리한 v5라 파일이 자동 적용되지 않는다(ADR-0018). `event`를 dictsync(ADR-0023)의 추가 항목(기본 적용)으로 넣었다. 실데이터 DB의 `propose_schema`는 `event:applied_at`, `event:viewed_at` 두 항목을 제안한다. 적용은 사용자 승인 뒤에 한다.
- **실데이터 사본에서 찾은 버그를 고쳤다.** 이관 이벤트는 대부분 시각 없이 날짜만 있다(at_precision date / unknown). 이벤트 시각이 NULL이면 기록은 날짜로 올바르게 계산됐지만, 경고의 "날짜로 잰 기록" 수에서 빠졌다. 그래서 "이벤트 시각으로 쟀다"는 잘못된 경고가 나왔다. 확인식을 NULL에 안전하게 고치고, 모든 기록이 날짜로 계산되면 "날짜로 쟀다"고 쓰게 했다. 사본에서 양쪽 날짜가 있는 11건 중 2건은 이벤트 시각으로, 9건은 날짜로 계산되었다.
