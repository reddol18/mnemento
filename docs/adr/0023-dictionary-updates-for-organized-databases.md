# ADR-0023: 정리된 DB에 저장소 사전 개선을 반영하는 경로

- 상태: **승인** (이슈 https://github.com/reddol18/mnemento/issues/12, 사용자 지시로 처리 2026-10-07)
- 보완: [ADR-0018](0018-elapsed-filter-and-vague-defaults.md) §5에서 "별도 과제"로 남긴 부분

## 맥락
사용자가 한 번이라도 정리(ADR-0014 승인)한 종류는 DB가 사전의 정본이다. 시작할 때 저장소 스키마 파일이 DB와 다르면 파일을 적용하지 않고 경고만 남긴다(ADR-0018). 사용자의 결정을 덮어쓰지 않으려는 규칙이다. 그 결과 저장소에서 개선한 설명·라벨·기본값이 실사용 DB에는 영영 들어가지 않았다.

## 결정
1. **시작할 때 건너뛴 파일을 기억한다.** `load_dir`가 정리된 종류의 파일을 적용하지 않을 때, 그 정의를 `skipped_files`에 둔다. 메모리에만 두며, 다음 시작 때 다시 읽는다.
2. **차이를 항목별 제안으로 보여 준다.** `propose_schema`가 `update_dictionary` 제안을 돌려준다. 제안 id는 `dict_<종류>_v<DB 버전>_<항목 지문>`이다. 항목은 세 갈래로 나뉜다.
   - **기본 적용(추가형)**: 새 선택 필드, 라벨이 있는 새 enum 값, 라벨·키워드 추가, DB에 없는 모호한 말의 기본값·관계 설명, 색인, 식별자 표시, 기본 날짜 필드(DB에 없을 때), implies(DB에 없을 때)
   - **골라야 적용(교체형)**: 필드·종류 설명의 교체, 이미 있는 기본값 읽기·기본 날짜 필드의 교체
   - **적용 불가(보고만)**: 타입·형식 변경, 새 필수 필드, 라벨 없는 enum 값
3. **승인은 기존 도구로 받는다.** `apply_schema_proposal(dict_…, approved_by, user_answer, items?)`를 쓴다. `items`가 없으면 추가형 항목만 적용한다. 결과는 추가형 새 버전으로 등록하고, 승인 기록(`schema_changes`)에 적용 항목과 거절 항목을 남긴다.
4. **거절한 항목은 다시 묻지 않는다.** 같은 파일 내용(항목 지문)에 대해서는 다시 제안하지 않는다. 파일이 또 바뀌면 바뀐 항목만 새로 제안한다.

## 근거
- DB가 정본이라는 ADR-0018의 원칙을 지키면서 개선을 받을 길을 연다. 사용자의 결정을 덮는 항목은 사용자가 직접 골라야 한다.
- 추가형 항목은 기존 기록과 질의를 바꾸지 않는다(ADR-0005의 추가형 변경). 그래서 기본값으로 둘 만하다.

## 대안
| 대안 | 기각 이유 |
|---|---|
| 파일을 통째로 적용할지 묻기 | 사용자가 정리한 설명·라벨까지 한 번에 덮인다 |
| 3-way 병합(이전 파일 버전 기준) | 이전 파일을 DB가 보관하지 않는다. 항목별 확인이 더 단순하다 |
| 거절 항목을 매번 다시 제안 | 시작할 때마다 같은 질문이 반복된다 |

## 결과
- 실사용 DB에도 저장소의 사전 보강(예: ADR-0018의 상태 설명, 모호한 말의 기본값)을 승인을 거쳐 넣을 수 있다.
- 제안은 MCP 서버가 시작할 때 읽은 파일 기준이다. 파일을 바꾼 뒤에는 서버를 다시 시작해야 새 차이가 보인다.
