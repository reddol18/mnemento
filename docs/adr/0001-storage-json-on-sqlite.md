# ADR-0001: 저장소 — JSON 문서 + 스키마 사전, SQLite 위에

- 상태: 채택 · 2026-10-02

## 맥락
에이전트마다 기록 형태가 다르고 계속 늘어난다(지원 기록, 투자 판단, 산출물…). 고정 테이블(RDB)은 새 종류마다 스키마 변경이 필요하다. 반면 순수 NoSQL은 유연하지만, LLM이 **어떤 필드가 있는지 모른 채 질의를 짐작**하게 된다 — 일반 DB에 MCP를 붙였을 때 정확도가 낮았던 근본 원인이다.

## 결정
- 문서는 **JSON 그대로** 저장(유연성).
- 기록 종류마다 **스키마 사전**(JSON Schema + 필드 설명 + 허용값)을 둔다. Keeper가 쓰기 검증과 질의 생성 모두에 이것을 쓴다.
- 자주 거르는 필드는 **생성 컬럼 + 인덱스**로 꺼낸다.
- 엔진은 **SQLite**(JSON1, WAL). 저장소 계층을 인터페이스로 감싸 Postgres JSONB로 교체 가능하게.

## 근거
- 쓰기 주체가 Keeper 하나(ADR-0002)라 SQLite의 동시 쓰기 제약과 무관. WAL로 읽기는 동시 가능.
- 개인 규모(수만~수십만 건)에서 인덱스 질의는 ms 단위.
- 서버 없이 파일 하나 — 설치·백업·공개 데모가 쉽다.

## 대안
| 대안 | 기각 이유 |
|---|---|
| 순수 RDB | 기록 종류 추가마다 마이그레이션 |
| MongoDB 등 | 별도 서버, 스키마 부재로 LLM 질의 정확도 저하 |
| 벡터 DB 단독 | 조건 질의("열람됐는데 결과 없는 곳") 불가 |

## 결과
- 스키마 사전 관리 비용이 생긴다 → 스키마 등록/변경을 Keeper 도구로 제공.
- 다중 사용자 서버가 필요해지면 Postgres 어댑터로 이행.
