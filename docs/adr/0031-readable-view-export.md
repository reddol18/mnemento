# ADR-0031: 사람이 읽는 보기용 DB를 스키마 사전으로 만든다 (`mnemento-db`)

- 상태: **승인** (사용자 직접 요청 2026-11-12)

## 맥락
장부에 무엇이 들어 있는지 LLM 없이 직접 보고 싶을 때가 있다. 그런데 원본 DB는 사람이 읽기 어렵다.

- 필드가 `entities.doc` JSON 안에 있다. 값은 코드(`saramin`, `viewed`)이고, 참조는 id(`co_004`)다.
- 원본을 SQLite 뷰어로 열면 JSON 문자열이 한 칸에 통째로 보인다. 어느 회사인지, 상태가 무엇인지 읽으려면 사람이 직접 풀어야 한다.
- 원본에 SQL 뷰를 만들면 저장소를 고치는 것이 된다. 그러면 Keeper만 쓴다는 규칙(ADR-0002)이 깨지고, 스키마가 바뀔 때마다 뷰도 다시 만들어야 한다.
- 스키마 사전에는 이미 필요한 정보가 다 있다. 필드 순서, 값마다의 라벨(`labels`), 참조 대상(`ref`), 설명(`description`)이다.
- DB가 어디 있는지도 찾기 어렵다. 위치는 MCP 설정의 `MNEMENTO_DB`에 흩어져 있다(사용자 설정, 프로젝트별 설정, Claude Desktop).

## 결정
1. **원본은 읽기 전용으로 열고, 보기용 DB를 따로 만든다.** 기본 위치는 `<DB 폴더>/views/<이름>-view.db`다. 만들 때마다 새로 만드는 스냅숏이다. LLM은 쓰지 않는다.
2. **기록 종류마다 평평한 표를 하나씩 만든다.**
   - 컬럼은 `id`, `display_name`, 스키마 필드(사전 순서), 사전에 없는 필드(draft), `created_at`, `updated_at` 순서다.
   - 값 코드는 첫 번째 라벨로 바꾼다(`saramin` → 사람인).
   - 참조는 대상의 이름으로 바꾼다. 이름은 대상의 `name`, 없으면 `title`, 없으면 `code`를 쓴다. 이때 컬럼 이름에서 `_id`를 뗀다(`company_id` → `company`).
   - `display_name`은 기록 자신의 이름이다. 자기 이름이 없는 기록(지원 건)은 첫 번째 참조 대상의 이름(회사명)을 쓴다. 컬럼 이름을 `name`으로 하지 않은 이유는 `name` 필드를 가진 스키마(company)와 겹치기 때문이다.
   - 무효화된(retracted) 기록은 빼고, 건수만 `_summary`에 남긴다.
3. **시계열 종류(`kind: series`)는 측정점 하나가 한 줄인 표로 만든다.**
4. **보조 표를 둔다.**
   - `_summary`: 종류별 건수, 무효화 건수, 마지막 갱신, 설명
   - `_fields`: 필드의 타입, 참조, 라벨, 필수 여부, 설명, 출처(schema/draft)
   - `_history`: 모든 이벤트. 변경 내용에도 라벨과 이름을 적용한다(`-> 열람`, `corrected: applied_at=...`).
   - `_meta`: 원본 경로, 원본 수정 시각, 만든 시각
5. **DB 찾기.** 다음에서 찾는다.
   - `~/.claude.json`(사용자 설정과 프로젝트별 설정), 현재 폴더의 `.mcp.json`, Claude Desktop 설정 파일의 `MNEMENTO_DB`
   - 환경 변수 `MNEMENTO_DB`
   - `~/.mnemento/*.db`
   - `--scan DIR` 아래의 Mnemento DB. `entities`·`events`·`schemas` 표가 있는 것만 Mnemento DB로 본다.
   목록의 `view` 칸에는 보기용 DB를 만든 시각을 보여 준다. 그 뒤에 원본(또는 `-wal`)이 바뀌었으면 `(stale)`를 붙인다.
6. **열기.** VS Code의 `code` 명령이 있으면 그것으로 열고(SQLite 뷰어 확장과 함께 쓰는 것을 전제로 한다), 없으면 운영체제의 기본 앱으로 연다. `--no-open`은 만들기만 한다.
7. **보기용 DB가 잠겨 있을 때.** Windows에서는 뷰어가 파일을 잡고 있을 수 있다. 그러면 옆에 시각을 붙인 새 파일로 만들고, 목록은 가장 최근 파일을 기준으로 보여 준다.

## 근거
- 저장소에 쓰지 않으므로 Keeper 단일 writer와 이벤트 불변 규칙을 건드리지 않는다.
- 라벨·참조·설명은 질의 파이프라인이 LLM에 보여 주는 바로 그 사전에서 온다. 그래서 사람이 보는 표와 LLM이 보는 사전의 용어가 같다.
- 스냅숏이라 스키마가 바뀌어도 마이그레이션할 것이 없다. 다시 만들면 된다. 실제 장부 규모(기록 약 800건, 시계열 약 5,800점)에서 만드는 데 1초가 걸리지 않는다.

## 대안
- **원본에 SQL 뷰 만들기**: 원본에 쓰게 되고, 스키마 버전마다 다시 만들어야 하며, 라벨은 SQL로 표현하기 번거롭다. 기각.
- **HTML 보고서**: 보기는 좋지만 사용자가 이미 쓰는 SQLite 뷰어의 정렬·필터·SQL 실행을 다시 만들어야 한다. 필요해지면 보기용 DB 위에 얹을 수 있다.
- **MCP `query` 도구로 보기**: 질문 단위라 전체를 훑어보기에 맞지 않고, 자연어로 물으면 토큰이 든다.

## 결과
- `mnemento-db list | open | view` CLI(`src/mnemento/viewdb.py`)와 테스트(`tests/test_viewdb.py`)가 생긴다. 테스트는 가상 데이터만 쓰고, 원본 파일의 해시가 바뀌지 않는 것까지 확인한다.
- 사전에 없는 값(예: enum에 없는 상태 코드)은 코드 그대로 보인다. 그래서 사전을 정리해야 할 곳이 눈에 띈다.
