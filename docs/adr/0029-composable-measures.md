# ADR-0029: 조립식 측정값·조건 — 계산 종류를 이름으로 늘리지 않는다

- 상태: **제안** (지휘부 검토 의견 반영 2026-10-12, 사용자 승인 대기. https://github.com/reddol18/mnemento/issues/17 · https://github.com/reddol18/mnemento/issues/18 · https://github.com/reddol18/mnemento/issues/19 를 대신함)

## 맥락
측정값의 계산 종류(`agg`)는 완성된 이름을 하나씩 등록하는 방식이다. `avg_days_between`(날짜 필드 간 평균 일수)과 `avg_hours_between_events`(이벤트 간 평균 시간)가 그렇다. 새 조합이 필요할 때마다 이름이 하나씩 늘었다. 미노출 v5(Haiku 4.5 고정, 4/6)에서 틀린 두 문항이 이 구조 때문이었다.

- Y4는 "기다린 시간을 다 합치면"을 물었다. 합계 × 시간 간격이라는 이름이 없어서 건수로 답했다.
- Y2는 "결과(passed 또는 rejected)에 도달한"을 물었다. `reached` 필터가 상태를 하나만 받아서 되묻기로 끝났다. 주 단위는 시도하기도 전이었다.

같은 개념이 곳곳에 따로 있다.
- 두 시점 사이 간격은 조건(`Elapsed`: `TimePoint` start/end + unit)에는 있다. 측정값에는 평균 두 종류로만 있다.
- 여러 값 받기는 이벤트 참조(`EventRef.to`, #16)에는 있지만 `reached`에는 없다.
- 단위는 `Literal["days","hours"]`가 측정값과 조건에 따로 있다.

참고 사항이 하나 있다. 일반적으로 LLM에게 SQL을 직접 쓰게 하면(text-to-SQL) 소넷급 이상이 필요하다는 경험이 있다. Mnemento가 제한된 명세(QuerySpec)를 쓰는 이유가 이것이다. 이 방식에서는 Haiku 4.5도 dev 27/28을 냈다. 자유도를 올리면 그만큼 text-to-SQL에 가까워진다.

## 결정 (제안)
1. **간격을 하나의 값으로 만든다.** 측정값에 `span: {start: TimePoint, end: TimePoint}`를 둔다. 조건의 `Elapsed`와 같은 `TimePoint`를 쓴다(필드 / 이벤트 / 오늘).
2. **집계와 대상을 분리한다.**
   - 측정값은 `agg ∈ {count, sum, avg, min, max, median}`이다.
   - 대상은 `field`, `span`, 계산 값(`Value`) 중 하나다.
   - 예: 평균 열람 시간 = `avg` + `span(created → status_changed:viewed)`, 대기 일수 합계 = `sum` + 같은 span + `unit: days`.
   - **중앙값을 포함한다.** "보통 며칠"은 자주 나오는 말이다(v4 X8은 중앙값을 인정 대안으로 두었다). 집계 이름이 하나 늘 뿐 문법 깊이는 그대로다. SQLite에 MEDIAN이 없으므로 SQL 생성 쪽에서 구현한다. 백분위수(p90 등)는 범위 밖이다.
   - **`count_if`는 프롬프트에서 뺀다.** 같은 뜻이 `count` + 측정값별 조건(`where`/`elapsed`, ADR-0027)으로 이미 있다. 같은 뜻을 두 방식으로 쓸 수 있으면 작은 모델이 둘 사이에서 흔들린다. 기존 명세와 캐시를 위해 검증 단계에서 `count` + `where`로 바꾸는 별칭으로만 남긴다.
   - **값 하나와 기록 하나를 구분한다.** "가장 오래 걸린 시간은?"은 `max` 집계(값 하나)다. "가장 오래 걸린 지원은?"은 목록 + span 정렬 + 1건(기록 자체)이다. 해석 프롬프트에 둘을 나란히 보이는 예시를 둔다.
3. **단위는 표로 둔다.** `hours / days / weeks`를 한 표(초 단위 환산)로 정의하고 측정값과 조건이 같이 쓴다. 새 단위는 표에 한 줄을 추가하면 된다.
4. **목록 값은 공통 규칙이다.** 값 하나를 받는 비교 연산은 모두 목록도 받는다.
   - `eq` + 목록 = 그중 하나(`IN`). `ne` + 목록 = 그 어느 것도 아님(`NOT IN`). "끝나지 않은" = `ne [passed, rejected, withdrawn]`이다(v5 Y6).
   - `reached` + 목록 = 그중 하나에 한 번이라도 도달했다(이력 기준).
   - 이벤트 상태(`EventRef.to`) + 목록 = 그중 어느 상태로 처음 바뀐 시각(#16).
   - 기존 `in` / `not_in`은 같은 뜻의 별칭으로 남기고 프롬프트에는 한 방식만 보인다.
5. **정밀도 검사는 한 곳에서 한다.**
   - 각 `TimePoint`는 정밀도(날짜 / 시각)를 가진다. 간격의 정밀도는 양 끝 중 낮은 쪽이다.
   - 날짜 정밀도인 간격에 시간 단위를 쓰면 거절한다. 2f2f6c8의 규칙을 조합마다가 아니라 한 번만 검사한다.
   - **이벤트가 없는 기록은 빼고, 몇 건 뺐는지 알린다.** 예를 들어 이관 데이터에는 viewed 이벤트 없이 `viewed_at` 날짜만 있을 수 있다. 이벤트 시점을 쓴 간격에서 그 이벤트가 없는 기록은 집계에서 빼고, 답에 "이벤트 시각이 없는 N건 제외"라고 경고한다. 날짜로 몰래 대신 계산하지 않는다. 같은 질문이 기록 상태에 따라 조용히 다른 정밀도로 계산되는 일을 막기 위해서다. 날짜로 계산하려면 해석기가 날짜 필드 시점을 명시적으로 고른다(일 단위만 허용).
6. **얕은 조립만 허용한다.** 조립은 "집계 + 대상 + 단위 + 조건" 한 단계다. 식의 중첩, 집계 안의 집계, 서로 다른 엔티티 간 간격은 이번 범위가 아니다. 작은 모델이 고를 칸의 수는 늘어도 문법 깊이는 그대로 둔다.
7. **호환한다.** `avg_days_between` / `avg_hours_between_events`는 별칭으로 남긴다. 검증 단계에서 새 형태로 바꾸므로 계획 캐시와 기존 명세가 그대로 동작한다. 프롬프트에는 새 형태만 보인다.
8. **표현할 수 없으면 비슷한 것으로 대신 답하지 않는다.** v5 Y4의 진짜 문제는 기능이 없었다는 것보다 건수 31을 답으로 낸 것이다. 조립식으로 바꿔도 범위 밖 질문(다른 엔티티 간 간격, 중첩 집계)은 계속 들어온다.
   - 해석기는 측정값보다 먼저 질문이 묻는 답의 모양을 적는다: `asks: {calc: sum|avg|median|min|max|count|list, unit: hours|days|weeks|null}`.
   - 검증 단계는 `asks`와 고른 측정값(집계·단위)이 맞지 않으면 이유를 붙여 거절한다. 해석기는 이유를 보고 한 번 다시 쓴다.
   - 맞는 표현이 없으면 해석기는 `unsupported`(이유 포함)를 낸다. 답은 "이 질문은 지금 기록 구조로 계산할 수 없다 + 이유"이고, 되묻기(clarify)와 구분해서 집계한다.
   - 벤치는 표현 불가 문항에 정직한 `unsupported`를 정답으로 친다.
9. **모델 기준은 측정으로 정한다.**
   - 기본 해석 모델은 Haiku로 둔다.
   - 바꾼 뒤 dev 회귀와 새 미노출 세트를 Haiku 4.5(고정), Sonnet, Opus로 같이 돌린다. 정확도와 함께 문항당 비용과 지연(평균·p95)을 기록한다.
   - Haiku 점수가 지금(dev 27/28)보다 떨어지면 프롬프트·검증 피드백으로 먼저 보완한다. 그래도 안 되면 해석 단계만 Sonnet으로 올리는 안을 따로 보고한다.

## 근거
- #17–#19가 각각 "새 이름 하나"가 아니라 기존 부품의 조합이 된다. 다음에 나올 "최소 / 최대 / 중앙값 대기 시간"도 추가 작업이 없다.
- 이미 있는 부품(`TimePoint`, `EventRef`, `Value`)을 측정값에 열어 주는 일이라 새 개념이 거의 없다.
- 검증을 정밀도 같은 값의 성질로 하면 규칙 수가 조합 수에 비례하지 않는다.

## 대안
| 대안 | 기각 이유 |
|---|---|
| 지금처럼 이슈마다 이름 추가 (#17–#19 따로) | 조합이 늘 때마다 같은 일이 반복된다. 검증 규칙도 이름마다 생긴다 |
| LLM이 SQL을 직접 쓰기 | 검증과 근거 제시(ADR-0001~)가 깨지고, 소넷급 이상이 필요해질 가능성이 크다 |
| 임의 중첩 식 문법 (식 트리) | 표현력은 가장 크지만 작은 모델의 오답 여지가 커진다. 필요한 질문이 나오면 그때 단계적으로 연다 |

## 결과 (예상)
- 바꿀 곳:
  - 명세(`spec.py`)
  - SQL 생성(`compile.py`)
  - 해석 프롬프트(`interpret.py`)
  - 답 변환기(`bench/runners.py`)
  - 테스트
- 이슈 하나보다는 크다. 위험은 작은 모델 정확도이고, 9번의 측정으로 확인한다.
- 검증용 새 미노출 세트는 지휘부가 쓴다.
  - 조립 조합: sum / min / max / median × span × 단위(weeks 포함), 목록 `reached`, `NOT IN`
  - 표현 불가 2문항: 다른 엔티티 간 간격, 중첩 집계
- 다른 엔티티의 날짜와 비교하는 질문(v4에서 뺀 마감일 문항)은 여전히 표현할 수 없다.
