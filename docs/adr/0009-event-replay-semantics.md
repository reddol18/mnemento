# ADR-0009: 이벤트 재생 규칙 — 정정은 대상 이벤트의 payload 교체, 적용 순서는 발생 시각

- 상태: 채택 · 2026-10-03

## 맥락
ADR-0003·0007은 "events에서 현재 상태를 언제든 재생성"하고 "정정은 `corrected`, 무효화는 `retracted` 이벤트로" 한다고 정했다. 구현하려면 이벤트를 어떤 순서로, 정정·철회를 어떻게 반영해 재생하는지 정확히 정해야 한다. 이게 모호하면 같은 이벤트에서 다른 상태가 나와 근거 제시가 무의미해진다.

## 결정
1. **payload 형식**
   | kind | payload |
   |---|---|
   | `created` | 문서 전체 |
   | `updated` | 바꿀 필드만. 값이 `null`이면 그 필드 삭제 |
   | `status_changed` | `{to, from?}` — `from`을 주면 현재 상태와 다를 때 **충돌로 거부**(저장 안 함) |
   | `corrected` | `{target, payload}` — `target` 이벤트가 **원래 이렇게 기록됐어야 했다**는 교체 payload |
   | `retracted` | `{}` = 엔티티 전체 철회 / `{target}` = 그 이벤트 하나만 무효 |
2. **재생 순서** — ① `retracted`로 무효 이벤트 집합을 만든다 ② 무효가 아닌 `corrected` 중 기록 순서(seq)상 가장 나중 것이 대상의 payload를 교체 ③ 데이터 이벤트(`created`·`updated`·`status_changed`)를 `created` 먼저, 그다음 **발생 시각 `at`(UTC)**, 같으면 seq 순으로 적용한다. 나중에 소급 기록한 이벤트(어제 열람된 걸 오늘 기록)도 실제 순서대로 반영된다.
3. **쓰기 = 재생** — `record_event`는 새 이벤트를 포함해 그 엔티티의 전체 이벤트를 재생하고, 결과 문서를 **최신 스키마로 검증**한 뒤 통과해야만 이벤트 추가 + 현재 상태 저장을 한 트랜잭션으로 한다. 그래서 증분 갱신과 `rebuild`가 정의상 같다.
4. **제약** — `created` 이벤트는 철회 대상이 될 수 없다(엔티티 전체 철회 사용). 철회의 철회는 불가. 정정·철회는 `evidence`(사유) 필수. 철회된 엔티티에는 더 이상 이벤트를 기록할 수 없다. 정정을 철회하면 원래 payload로 돌아간다.
5. **엔티티 타입** — `record_event(entity_id, kind, payload, at, by, evidence)`에 키워드 인자 `entity_type`을 추가했다. `created`에서 필수(스키마 선택), 그 외에는 주면 일치 여부만 확인.
6. **인덱스 필드** — 스키마 사전에서 `indexed: true`인 필드는 `entities`에 `f_<필드명>` VIRTUAL 생성 컬럼(`json_extract(doc,'$.<필드>')`)과 `(type, f_<필드>)` 인덱스로 꺼낸다. 같은 이름의 필드는 타입 간에 컬럼을 공유한다.

## 근거
- 정정을 "패치"가 아니라 "대상 payload 교체"로 하면 의미가 하나로 정해지고(무엇이 원래 맞았나), 정정 이력이 쌓여도 마지막 것만 보면 된다.
- 기록 순서가 아니라 발생 순서로 적용해야 "지원 → 열람"을 거꾸로 기록해도 상태가 맞는다.
- 검증을 재생 결과에 하므로 정정이 뒤 이벤트와 모순되면(예: `from` 불일치) 저장되지 않고 되물을 수 있다 — "불확실하면 저장하지 않는다"(ADR-0002).

## 대안
| 대안 | 기각 이유 |
|---|---|
| 정정 = 정정 시점에 적용하는 패치 | 대상 이벤트 이후 이벤트와의 관계가 모호, "원래 기록이 뭐였어야 했나"를 답 못 함 |
| 기록 순서(seq)로 재생 | 소급 기록 시 상태가 틀림 |
| 현재 상태만 증분 갱신 | 재생 결과와 어긋날 위험, rebuild 동일성 보장이 어려움 |

## 결과
- 엔티티당 쓰기마다 그 엔티티의 이벤트 전체를 재생한다 — 개인 규모(엔티티당 수~수십 건)에선 무시 가능.
- `status_changed`는 스키마에 `status` 필드가 있는 타입에만 의미가 있다.
- 소급 기록한 이벤트나 정정이 그 뒤 `status_changed`의 `from` 검사와 어긋나면 `ConflictError`로 저장되지 않는다. 이때 Keeper(기록 도구)는 오류로 끝내지 않고 **되묻기**로 처리한다(충돌한 이벤트와 현재 상태를 보여 주고 선택지 제시).
