# ADR-0021: MCP로 새 기록 종류 만들기 — 기록과 스키마 초안을 함께 제출

- 상태: **승인** (이슈 https://github.com/reddol18/mnemento/issues/6, 방향은 사용자 제안 2026-10-06, 처리 2026-10-07)
- 확장: [ADR-0014](0014-store-first-organize-later.md)(먼저 저장하고 나중에 정리)를 필드·값에서 **종류**로 넓힌다

## 맥락
등록되지 않은 종류(예: 독서 메모)를 `record`하면 "Unknown record type"으로 거부됐다. ADR-0014의 "먼저 저장"은 이미 있는 종류의 새 필드·값에만 적용됐다. `propose_schema(samples)`는 초안만 돌려주고 proposal id가 없어서 `apply_schema_proposal`로 적용할 수 없었다. 결국 새 종류는 로컬 스크립트로만 등록할 수 있었다. MCP로 쓰려는 도구가 MCP로 핵심 흐름을 끝내지 못하는 셈이었다.

## 결정
1. **기록과 스키마 초안을 함께 보낸다.** 새 종류의 첫 `record`(kind=created, 구조화 요청)에 에이전트가 `schema_draft`를 함께 보낼 수 있다. 초안에는 설명, 키워드, 필드(type·description·enum·labels·required·indexed·format)가 들어간다.
2. **draft 종류로 즉시 저장한다.** 그 종류를 `status: "draft"` 스키마로 등록한다. 이 스키마는 필드가 없고 아무것도 강제하지 않는다. 모든 필드는 ADR-0014의 draft이므로, 기록은 바로 저장되고 바로 조회된다. 해석기 사전에는 "NEW TYPE, not approved yet"으로 보인다.
3. **초안은 승인 대기 제안이다.** 초안은 draft 스키마의 `proposal`에 버전과 함께 보관한다. 제안 id는 `type_<이름>_v<버전>`이다. draft 종류에 기록할 때마다 응답의 `proposals`와 `questions`에 승인 질문이 붙는다. 초안을 보내지 않으면 저장된 기록에서 초안을 추론한다(설명은 승인 때 받는다). 나중에 다른 초안을 보내면 버전이 올라가고 제안 id도 바뀐다.
4. **사용자 승인으로 정식 등록한다.** `apply_schema_proposal(id, approved_by, user_answer, descriptions, labels, index, type_description)`로 등록한다. 필수 필드·enum·색인은 이때부터 강제된다. 다음 경우에는 등록을 거부한다.
   - 설명이 없는 필드가 있다
   - 라벨이 없는 enum 값이 있다
   - 저장된 기록이 새 스키마에 맞지 않는다(맞지 않는 기록을 나열한다)
   - draft 종류는 강제한 것이 없었으므로, draft → 등록은 파괴적 변경 검사에서 제외한다
5. **이름 파편화를 막는다.** 새 종류 이름이 기존 종류 이름이나 키워드와 비슷하면 저장하지 않고 되묻는다(clarify). 같은 종류인지 묻고, `new_type=true`로 확인해야 만든다. ADR-0014는 필드는 저장하고 묻는데, 종류는 저장하지 않고 묻는다. 같은 기록이 두 종류로 나뉘면 모든 집계가 갈라지기 때문이다.
6. **범위.**
   - 새 종류는 구조화 요청으로만 만든다. 자유 서술 경로(`record` text)는 만들지 않는다. 모델이 종류를 지어낼 수 있기 때문이다.
   - 새 종류는 created 기록으로만 시작한다.
   - series 종류는 이 경로로 만들지 않는다(ADR-0016: 먼저 사용자와 등록).

## 근거
- 필드 설명을 쓰기 가장 좋은 때는 맥락을 가진 첫 기록 순간이다. 그래서 초안은 그때 받는다.
- 승인 대상은 강제력이 생기는 등록 하나로 남긴다. 저장과 조회는 승인을 기다리지 않는다(ADR-0014와 같은 원칙).

## 대안
| 대안 | 기각 이유 |
|---|---|
| `propose_schema(samples)`에 proposal id만 붙이고 기록은 승인 뒤에 | 승인 전까지 기록이 남지 않는다(ADR-0014가 버린 보류함과 같은 문제) |
| 새 종류를 바로 정식 등록 | 사용자 승인 없이 강제력이 생긴다(공통 원칙 위반) |
| 비슷한 종류 이름도 저장하고 묻기(필드와 같게) | 종류가 갈라지면 집계 전체가 갈라진다. 되돌리려면 기록을 옮겨야 한다 |

## 결과
- MCP만으로 새 종류의 기록 → 조회 → 승인 → 강제가 끝까지 된다.
- 새 종류에 기록할 때마다 승인 질문이 붙는다. 사용자가 미루면 응답이 조금 길어진다.
