# Mnemento 기획서

> *Like Leonard's polaroids in Memento — a shared, structured record book for LLM agents.*
> 작성 2026-10-02 · 상태: 설계 합의(v0), 구현 전

## 1. 배경 — 왜 만드는가

LLM 에이전트는 영화 메멘토의 레너드처럼 **중기 기억이 끊긴다.** 세션이 끝나거나 대화가 요약되면 맥락이 사라지고, 결국 외부 메모에 의존해 판단한다.

실제로 겪은 문제 (작성자의 개인 에이전트 운영 중, 2026-10):
- 기록이 **형식이 다른 여러 곳에 흩어짐** — 메모리 마크다운, HTML 속 JSON, 산출물 대장 훅, 웹 페이지의 localStorage.
- 그 결과 **"오늘 구직 플랫폼에 지원한 곳이 몇 곳?"을 하나 적게 셈**. 메모의 애매한 문구를 "패스"로 오판했고, 지원완료 메일이라는 근거와 대조할 수단이 없었다.
- **"이 회사에 예전에 지원했나?"**에 답하려고 HTML·대화 기록을 grep 해야 했다.
- 일반 DB에 MCP를 붙여 자연어로 물으면, LLM이 **스키마를 몰라 질의를 짐작**해서 부정확했다.

기존 에이전트 메모리(mem0 OpenMemory, Supermemory, Letta)는 대부분 **비슷한 문장을 찾아오는 벡터 검색**이라 조건 질의에 약하다. Zep은 스키마(엔티티 타입)를 지원하지만 타입·필드 10개 제한, 그래프 질의 방식이다.

## 2. 목표 / 비목표

**목표**
1. 여러 에이전트가 **하나의 장부**에 사실을 기록하고, 자연어로 물으면 **정확한 조건 질의**로 답한다.
2. 모든 답에 **근거(어떤 기록으로 셌는지)**를 붙인다.
3. 확실하지 않은 입력은 **저장하지 않고 되묻는다.**
4. 깃허브 공개용 **포트폴리오 품질**(설계 기록, 정확도 평가, 쉬운 설치).

**비목표 (v0)**
- 다중 사용자 서버, 클라우드 호스팅
- 에이전트의 "교훈·습관" 기억 (memento-mcp 류 — 우리는 사실 기록)
- 의미 검색 (v1에서 추가)

## 2-1. 성공 지표 — 정확도·속도·비용 (2026-10-03 사용자 정의)

Mnemento는 아래 세 가지에서 **"LLM 자체 메모리만 쓸 때"보다 나아야** 의미가 있다. 구현 목표이자, **실측 벤치마크로 README에 공개**한다.

| 지표 | 목표 | 측정 |
|---|---|---|
| **정확도** | LLM 자체 메모리보다 **같거나 높게** (낮으면 존재 이유 없음) | 평가 문항(`docs/eval/`) 정답률. 해석·질의·답변 근거까지 채점 |
| **속도** | 너무 느리지 않게, **가장 좋은 건 LLM 메모리만 쓸 때보다 빠른 것** | 질문당 응답 시간(평균·p95), 도구 호출 포함 전체 왕복 |
| **비용** | LLM 토큰 비용 **절감** | 질문당 입력·출력 토큰과 금액(모델 단가 기준) |

**비교 대상 (같은 모델·같은 문항·여러 번 반복)**
- **B0 전체 넣기**: 기록 전체를 컨텍스트에 넣고 묻기 (정확하지만 비싸고 느림의 기준선)
- **B1 파일 메모리**: 마크다운 메모리 + 파일 검색(grep·Read) — 작성자가 지금 실제로 쓰는 방식
- **B2 벡터 메모리**: mem0 OpenMemory 등 비슷한 문장 검색 방식 (가능하면)
- **M Mnemento**: 해석 → 질의 → 답변 파이프라인

**설계에 주는 함의 (비용·속도를 이기기 위한 원칙)**
1. LLM에는 **전체 데이터가 아니라 관련 스키마 일부와 집계 결과만** 보낸다 — 질의 실행은 SQLite가 한다.
2. 해석·질의 정의는 작은 프롬프트로, 정해진 형식(구조화 출력)으로 받는다.
3. 형식이 정해진 기록·질문은 **LLM 없이 코드로** 처리하는 경로를 둔다.
4. 같은 질문 패턴은 질의 계획을 재사용(캐시)한다.

방법론은 [ADR-0008](adr/0008-benchmark-methodology.md).

## 3. 구조

```
[투자 에이전트] [구직 에이전트] [영상 에이전트] ...
      │  자연어 또는 구조화 메시지 ("기록해줘" / "찾아줘")
      ▼
┌──────────────────────────────┐
│ Keeper (기록 저장 에이전트)     │  ← 저장소를 만지는 유일한 존재(single writer)
│  write: 정규화 · 스키마 검증 · 중복/동일 엔티티 판정 · 근거 기록
│  read : 자연어 → 질의 계획(스키마 사전 기반) → 실행 → 근거와 함께 응답
└──────────────────────────────┘
      ▼
SQLite (WAL) : schemas · events · entities(+생성 컬럼 인덱스)
```

- **핵심은 MCP 서버**로 만들고, 대화형 창구(Claude Code 세션 간 메시지)는 그 위에 얹는다. 두 경로 모두 지원.
- **쓰기 경로 분리:** 형식이 맞는 입력은 코드로 즉시 검증·저장, 자유 서술만 LLM이 구조화. (비용·지연 절감)

## 4. 데이터 모델 — "JSON 문서 + 스키마 사전 + 사건 기록"

| 테이블 | 내용 |
|---|---|
| `schemas` | 기록 종류별 JSON Schema + **필드 설명 + 허용값** (LLM이 질의 만들 때 보는 사전) |
| `events` | 모든 변화를 **덮어쓰지 않고 누적** — 누가(agent)·언제·무엇을·근거(evidence) |
| `entities` | events를 반영한 **현재 상태** 문서(JSON). 자주 거르는 필드는 생성 컬럼 + 인덱스 |

예시 (구직 도메인):
```json
// entity
{ "type": "application", "id": "app_saramin_10000001",
  "company_id": "co_gasang_media", "platform": "saramin", "posting_id": "10000001",
  "title": "풀스택 개발자(AI Agent)", "status": "viewed",
  "applied_at": "2026-10-02", "viewed_at": "2026-10-02",
  "expected_rate": "top10", "reason": "AI 개발 가능" }
// event
{ "entity": "app_saramin_10000001", "kind": "status_changed",
  "from": "applied", "to": "viewed", "at": "2026-10-02T17:40+09:00",
  "by": "job_agent", "evidence": "user: '가상미디어 열람'" }
```
- `company`를 별도 엔티티로 둬 **동일 회사 판정**("가상테크" = "(주)가상테크" = "Gasang Tech")을 한곳에서 한다.

## 5. 에이전트 대화 규칙

| 요청 | 예 | Keeper 동작 |
|---|---|---|
| record | "사람인 10000001 가상미디어 열람" | 대상 엔티티 찾기 → event 생성 → 현재 상태 갱신 |
| query | "열람됐는데 2주째 결과 없는 곳?" | 스키마 사전의 필드·허용값만으로 질의 생성 → 실행 |
| count | "오늘 사람인 지원 몇 곳?" | 숫자 + **근거 목록** |
| ambiguous | "가상테크 지원했어"(공고 2개) | 저장 안 하고 되묻기 |

원칙: ① 불확실하면 되묻기 ② 답에 근거 ③ 스키마에 없는 필드는 질의에 못 씀(환각 차단)

### 5-1. Keeper의 두 가지 핵심 역할 (2026-10-03 사용자 정의)

**A. 질문 처리 파이프라인 — 해석 → 질의 정의 → 답변 작성**

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| ① 해석 | 자연어 질문을 스키마 사전 용어로 번역. 기간·대상·비교 기준을 명시화, 모호하면 되묻기 | 질문 명세 (예: "상태=열람 이상, 기간=9월·10월, 예상합격률 등급별") |
| ② 질의 정의 | 명세를 실행 가능한 질의(여러 개 가능)로 계획. 스키마에 있는 필드·허용값만 사용 | 질의 계획 + 실제 SQL/필터 |
| ③ 답변 작성 | 결과를 해석해 답하고 **근거·한계**를 붙임 (표본 수, 미완료 데이터 등) | 답 + 근거 목록 + 주의사항 |

예시 질문 (2026-10-03 실제 대화): *"지난번에도 예상 합격률 10%대가 먼저 열람됐나?"*
→ ① 지원 건을 월(9월/10월)·예상합격률(상위10/30)로 나눠 열람 여부 비교 ② 그룹별 지원 수·열람 수 집계 ③ "지난달은 상위30% 쪽 열람률이 오히려 높았고, 이번 달은 상위10%가 앞서지만 30% 쪽은 지원 하루 경과라 판단 이름" + 표본 수 경고

**B. 스키마 설계 — 유연하게 대응하는 스키마를 정의**

- 새 종류의 기록이 들어오면 Keeper가 **스키마 초안(필드·타입·허용값·설명·인덱스 여부)을 제안**하고, 확정되면 등록한다.
- 기존 스키마에 맞지 않는 필드가 반복되면 **스키마 확장(추가형 변경, ADR-0005)을 제안**한다.
- 자주 쓰이는 질문 패턴을 보고 **인덱스 대상 필드나 파생 필드**(예: "열람까지 걸린 시간")를 제안한다.
- 원칙: 제안은 Keeper가, **확정은 사용자(또는 지휘 에이전트)**가 — 스키마가 조용히 바뀌지 않게.

## 6. 기술 선택

- Python 3.11+, uv, **SQLite (JSON1, WAL)**, MCP Python SDK
- 저장소 계층을 인터페이스로 감싸 **Postgres(JSONB) 전환 가능**하게
- 성능: 단일 writer라 SQLite 동시쓰기 약점과 무관, 개인 규모(수만~수십만 건)에서 인덱스 질의 ms 단위 → [ADR-0001](adr/0001-storage-json-on-sqlite.md)

## 10. 결정된 세부 규칙 (구 미결 사항, 2026-10-02 확정)

| 주제 | 결정 | ADR |
|---|---|---|
| 시간 표기 | 시각은 오프셋 포함 ISO 8601, "그날" 의미의 필드는 `YYYY-MM-DD`(사용자 시간대, 기본 Asia/Seoul). "오늘·어제"는 Keeper가 설정 시간대로 날짜 범위로 바꾸고 답에 표시. 발생 시각 `at`과 기록 시각 `recorded_at` 구분 | [0004](adr/0004-time-representation.md) |
| 스키마 진화 | 문서마다 `schema_version`. 추가형 변경은 버전만 올림, 파괴형 변경은 이행 스크립트가 `migrated` 이벤트로 변환. 스키마 사전 이력 보관 | [0005](adr/0005-schema-evolution.md) |
| 동일 엔티티 판정 | ① 외부 식별자 ② 정규화 이름 + 별칭 사전 ③ LLM은 후보 제안만, **자동 병합 금지**·되묻기. 병합은 `merged`/`unmerged` 이벤트로 되돌릴 수 있게 | [0006](adr/0006-identity-resolution.md) |
| 정정·삭제 | 정정은 `corrected` 이벤트, 잘못된 기록은 `retracted`로 무효화. 물리 삭제는 개인정보 요청 시 `purge` 명령으로만(삭제 사실만 기록) | [0007](adr/0007-correction-and-deletion.md) |

## 11. 남은 질문 (구현하면서 정함)

- Keeper가 되물을 때의 응답 형식(선택지 목록 vs 자유 서술)
- 평가셋 정답을 실데이터로 만들지, 공개용 가상 데이터로도 같은 문항을 만들지
